# Build a useful marketing experience

## Choose the smallest real implementation

Use the user's existing stack, design conventions, permissions, and artifact tools. Do not introduce a new hosting provider or paid service merely to demonstrate an idea. Use the relevant existing document, spreadsheet, web, presentation, or design skill where the deliverable requires it.

| Available material | Build now | State the limit |
| --- | --- | --- |
| Editable application | One working route/component and existing logic or narrow endpoint. | Local checks are not production deployment. |
| Product URL and verified facts | A complete local prototype or factual decision worksheet. | Do not imply private implementation access. |
| Local service and an operating process | A fit worksheet, sample itinerary, consultation with specified outputs, or transparent estimator. | Do not present an unstaffed process as operational. |
| No verified product facts | A labeled exploratory example and the minimum missing context. | Do not invent capabilities. |

An asset must let someone do its promised small job. A list of recommendations, empty form, fake result, or unconnected button is not complete.

## Preserve decision integrity

Define acceptance conditions before persuasive copy:

1. What can the person determine or accomplish?
2. Which inputs materially change the result?
3. Which information remains unknown?
4. Which conditions mean not-a-fit or insufficient information?
5. What next step fits each result?

Do not invent match percentages, diagnostic labels, or savings. For displayed numbers, expose formula, units, assumptions, and observed versus hypothetical inputs. Prefer an explicit constraint result over an arbitrary score.

For comparisons, include relevant supported alternatives, including doing nothing or manual work. Do not manipulate factual criteria so the sponsor always wins. Disclose the sponsor. Avoiding an unsuitable purchase can be the correct customer outcome.

## Reuse real product behavior

- Find the existing calculation, validation, business-rule, or service boundary.
- Reuse it when permitted; avoid an unmaintained duplicate formula.
- Match units, time zones, defaults, rounding, and error conditions.
- Verify representative equivalence cases, a boundary, and the not-a-fit path.
- Treat changing external data and nondeterministic outputs explicitly.
- Label synthetic demonstration data before results and in exports.

## Share only permitted information

Define a public schema using an allowlist. An opaque identifier is not authorization. Separate intentionally public examples, new recipient inputs, and private sender state. Keep credentials, personal records, account identifiers, internal notes, and proprietary rules out of shared artifacts.

Keep sensitive inputs out of URL queries, previews, logs, analytics payloads, and public exports. Use minimal aggregate measurement where sufficient. Do not add external tracking without a purpose and authorization.

Specify expiry, revocation, or deliberately permanent publication. Preserve meaning across product versions. Recipient edits must not mutate the sender's work or inherit their paid privileges.

Keep private computation server-side. Expose only the needed operation, with validation, appropriate access controls, quotas, cost ceilings, and abuse handling. State when a prototype only simulates these controls.

## Build the delivery path

Choose one reachable, permitted surface tied to the buying situation: an existing result, owned landing page, authorized conversation, customer touchpoint, or relevant channel with current rules. Do not default to scraped contact lists or unsolicited messages.

Prepare an invitation explaining the useful job, suitable audience, effort, and exact destination. Align public copy to inspected evidence. If an external action lacks authorization, finish the artifact and copy before requesting the remaining concrete action.

## Verify before marking ready

Run meaningful checks appropriate to the artifact:

- Complete the ordinary user job.
- Exercise not-a-fit and unknown results.
- Check invalid/missing inputs and reset/back behavior.
- Confirm recipient access cannot retrieve or overwrite private sender state.
- Confirm costly operations stop at declared limits.
- Check narrow-screen and keyboard behavior for interactive assets.
- Distinguish real functionality from simulated integrations.

Record artifact/version, commands or actions, and observed results. Correct code validates implementation; it does not establish demand, sales lift, trust, or virality.

Version the contract when the audience, offer, key claim, intervention, primary outcome, or design changes. Preserve unrelated work. A typo correction usually requires no new marketing experiment; a new promise or price can.
